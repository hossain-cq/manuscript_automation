# Secure Deployment and Docker/Kubernetes Guide

## Scientific manuscript system with LangGraph and sandbox support

## 1. Deployment objective

The production system should be deployed as a control plane plus a separate scientific execution plane. LangGraph belongs in the control plane. It orchestrates project intake, evidence assessment, literature grounding, manuscript drafting, human approvals, peer-review simulation, and revision workflows. DFT, quantum, model-training, and arbitrary project-code execution belongs in a separately isolated sandbox runner.

```text
User/API
  → Manuscript control plane
      ├── LangGraph orchestrator
      ├── PostgreSQL checkpoint and domain database
      ├── artifact/provenance service
      ├── literature provider adapters
      └── approval service
  → sandbox submission API
      → bounded DFT/quantum/analysis worker
          ├── read-only input artifacts
          ├── pinned profile/environment
          ├── isolated writable output
          ├── no network by default
          └── resource and time limits
```

The original project folder must not be mounted directly into a production pod or worker. It should be scanned and copied into a managed artifact namespace after the user explicitly selects the folder and the system records its boundary and checksums.

## 2. Trust boundaries

| Boundary | Trust decision |
|---|---|
| User project folder → intake scanner | Treat all filenames, text, notebooks, scripts, and metadata as untrusted data |
| Intake scanner → artifact store | Accept only registered files with checksums and size/type policies |
| LLM → application | Treat model output as an untrusted proposal; validate schemas and IDs |
| Control plane → sandbox runner | Submit typed, profile-based job specifications; never arbitrary commands |
| Sandbox runner → artifacts | Accept only declared outputs with checksums, logs, resource data, and parser status |
| External literature API → system | Treat metadata and abstracts as untrusted text; preserve provider provenance |
| Human approval → workflow | Store actor, timestamp, decision, affected artifacts, and policy version |

## 3. Recommended production components

| Component | Responsibility |
|---|---|
| API service | Authentication, project/run APIs, approval endpoints, health checks |
| LangGraph worker | Durable graph execution, interrupts, retries, routing, and state transitions |
| PostgreSQL | Checkpoints, projects, claims, evidence, findings, reviews, approvals, and metadata |
| Artifact store | Raw/derived files, figures, manuscript blocks, logs, checksums, and immutable versions |
| Sandbox runner | Profile-validated DFT/quantum/analysis jobs in restricted workers |
| Queue or scheduler | Long-running job dispatch, retry, timeout, cancellation, and resource scheduling |
| Observability | Structured logs, metrics, traces, model-call metadata, and audit events |
| Secret manager | LLM credentials, database credentials, provider keys, and connector secrets |

For a local prototype, Docker Compose is sufficient. For multi-user operation, long DFT jobs, hardware connectors, or strict isolation, use Kubernetes with a separate worker pool or stronger VM-based execution boundary.

## 4. Container build requirements

The supplied Dockerfile is a hardened starting point. In the actual repository:

1. Generate a complete dependency lock file with hashes.
2. Build from a pinned Python base image digest rather than a floating tag.
3. Scan the image for vulnerabilities in CI.
4. Run as a non-root UID.
5. Drop Linux capabilities and disallow privilege escalation.
6. Use a read-only root filesystem.
7. Use a small in-memory `/tmp` volume.
8. Do not copy project folders, SSH keys, cloud credentials, or local `.env` files into the image.
9. Do not include compilers or arbitrary package managers in the API image unless required.
10. Sign and verify production images before deployment.

The requirements file in this package is a template. A production build must replace it with a fully hashed lock file generated by the project’s dependency-management process.

## 5. Local Docker Compose deployment

Create a `.env` file outside version control:

```bash
POSTGRES_PASSWORD='use-a-random-long-secret'
OPENAI_API_BASE='https://your-approved-llm-proxy/v1'
OPENAI_API_KEY='your-secret'
```

Build and start the control plane:

```bash
docker compose -f deploy/docker-compose.yml build --pull
 docker compose -f deploy/docker-compose.yml up -d postgres runner api
```

Check service health:

```bash
docker compose -f deploy/docker-compose.yml ps
docker compose -f deploy/docker-compose.yml logs --tail=200 api runner
curl --fail http://127.0.0.1:8080/health/live
curl --fail http://127.0.0.1:8080/health/ready
```

The Compose network is internal by default. Bind the API to localhost during development. Do not expose the PostgreSQL or runner ports directly to the host.

## 6. Sandbox runner design

The runner should expose a narrow API such as `POST /v1/jobs`, `GET /v1/jobs/{job_id}`, and `POST /v1/jobs/{job_id}/cancel`. The request must contain a stored job-spec artifact ID and approved profile ID, not a shell command.

The runner should validate the specification twice: once in the control plane and again inside the runner. A profile registry should define allowed executables, parameter schemas, input artifact types, output expectations, environment lock hash, CPU/memory/time/output quotas, and network policy.

The runner should mount input artifacts read-only and write only to a unique per-job directory. It should calculate checksums before and after execution, retain raw output before parsing, record stdout/stderr, and register parsed outputs only when the parser passes validation.

The runner must not mount `/var/run/docker.sock`, host home directories, SSH keys, cloud credential directories, arbitrary project folders, or unrestricted host paths.

## 7. Container security for scientific jobs

For trusted, profile-driven workloads, a rootless container with a read-only root filesystem, dropped capabilities, seccomp, AppArmor or equivalent policy, disabled network, non-root user, and resource quotas is a reasonable starting point. For untrusted project code or high-consequence workloads, use a disposable VM or stronger isolation runtime. A Conda environment alone is not a security boundary.

Required controls include:

| Control | Minimum requirement |
|---|---|
| Identity | Non-root dedicated UID/GID |
| Filesystem | Read-only root; only job output writable |
| Input | Artifact-ID-based read-only mounts |
| Network | Disabled by default; explicit allowlist only |
| Credentials | No inherited host or user credentials |
| Resources | CPU, memory, process, disk, output, and wall-time quotas |
| Syscalls | RuntimeDefault seccomp; stronger policy for untrusted workloads |
| Capabilities | Drop all unnecessary capabilities |
| Reproducibility | Pinned image/environment and code revision |
| Cleanup | Remove temporary workspace after artifact commit |
| Audit | Job spec, policy decision, logs, checksums, usage, and approval |

## 8. Kubernetes deployment

The supplied manifest creates a dedicated namespace, restricted pod-security labels, service accounts without automatic tokens, API and runner deployments, PostgreSQL storage, artifact storage, default-deny networking, API-to-runner networking, runner no-egress networking, probes, resource limits, and a disruption budget.

Before applying it:

```bash
kubectl apply --dry-run=server -f deploy/k8s/manuscript-system.yaml
```

Replace the example secret values through an external secret manager. Do not commit real keys to the manifest. Then apply the deployment:

```bash
kubectl apply -f deploy/k8s/manuscript-system.yaml
kubectl -n manuscript-system get pods
kubectl -n manuscript-system rollout status deployment/manuscript-api
a kubectl -n manuscript-system rollout status deployment/sandbox-runner
```

The sample manifest is intentionally conservative but still requires environment-specific review. Kubernetes NetworkPolicy behavior depends on the installed CNI. Verify that the cluster enforces the intended policy rather than assuming that the YAML alone provides isolation.

## 9. Kubernetes hardening checklist

Use a dedicated cluster or node pool for heavy scientific execution. Apply Pod Security Admission at `restricted` or a stronger organization policy. Enforce signed images, admission policies, resource quotas, and namespace limits. Prefer a dedicated runner namespace if the DFT workload needs special CPU, memory, GPU, or scheduler access.

For very heavy DFT jobs, do not run long computations inside the API pod. Submit to a scheduler such as Slurm, a dedicated worker pool, or a VM-based execution service. Store the scheduler job ID and worker revision in the provenance record.

Protect the Kubernetes API, restrict service-account permissions, disable service-account token automount where not needed, and prevent the runner from creating pods unless a separately reviewed job-controller architecture is in place.

## 10. Database and artifact storage

PostgreSQL should store structured state, not large PDFs, raw simulation output, or figure binaries. Store artifacts in an object store or controlled persistent volume with immutable keys. Every artifact should include checksum, type, parent IDs, creator run, code revision, environment lock hash, creation timestamp, and retention policy.

Database backups should be encrypted, tested, and versioned. Artifact retention should distinguish raw source files, derived data, intermediate logs, manuscript blocks, final releases, and audit records.

## 11. Secrets and external providers

Secrets must be injected at runtime through a secret manager. They must never appear in prompts, graph state, artifact contents, job logs, environment manifests, or LLM-visible packets. The literature providers should receive only the minimum query and configured contact information. Cloud quantum credentials should be isolated in a connector service and require explicit human approval before hardware submission.

## 12. Observability and audit

Log structured events for graph start/resume/end, node start/end, LLM request metadata, structured-output validation, human interrupts, sandbox submission, job state, artifact registration, parser result, revision, and release approval. Do not log raw secrets or entire sensitive project files.

Useful metrics include graph duration, node retries, model validation failures, reviewer disagreement, artifact checksum failures, sandbox queue time, timeout rate, CPU/memory use, missing-evidence rate, and human-approval latency.

## 13. Backup and disaster recovery

Back up PostgreSQL, artifact metadata, raw source artifacts, final releases, and audit decisions. Test restoring a project run and resuming a LangGraph thread from its checkpoint. A valid recovery test must verify that an interrupted human approval can resume with the same thread ID and that artifact checksums remain stable.

## 14. Production release gates

A release should be blocked unless:

- Images are built from pinned dependencies and scanned.
- Secrets are externalized.
- API and runner health checks pass.
- Network policies are verified.
- Sandbox escape and unauthorized-file-access tests pass.
- The DFT integration test passes.
- Human approval and audit records are persisted.
- Backups and restore procedures are tested.
- The final manuscript package contains claim/evidence/provenance metadata.

## 15. Important limitation

The supplied deployment files are secure-by-default templates, not a substitute for a cluster-specific security review. The sandbox runner is the most sensitive component. If it will execute untrusted project code, use a stronger VM-level isolation design and an independent security assessment before enabling it in production.
